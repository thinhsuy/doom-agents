# infra — Terraform for deploying agency-agents

Minimal, cost-conscious AWS stack that runs the Agency OS app (FastAPI serving REST +
WebSocket + the built console) on **ECS Fargate**, backed by **RDS Postgres**, fronted by an
**ALB**, with an **S3** bucket and secrets in **SSM Parameter Store**. Everything is named
and tagged **`agency-agents`** (not `doom-agents`).

## What it provisions

| Resource | Sizing (minimal) | ~cost/mo* |
|---|---|---|
| VPC (2 public + 2 private subnets, IGW, **no NAT**) | — | $0 |
| ECS Fargate service (1 task) | 0.25 vCPU / 0.5 GB | ~$9 |
| ALB (stable URL, TLS-ready, WebSocket) | — | ~$16–20 |
| RDS Postgres (single-AZ) | `db.t4g.micro`, 20 GB gp3 | ~$12–15 |
| ECR, S3, CloudWatch Logs, SSM | tiny | ~$1–3 |

\* Rough `ap-southeast-1` estimate, ~**$40–50/mo**. The ALB + RDS are the fixed costs. No NAT
gateway (the usual hidden ~$32/mo) — the Fargate task gets a public IP instead.

## DB transport (already handled)

`company/api/db.py` and `company/ui/dbio.py` are **dual-transport**: locally they use
`docker exec psql`; when **`PGCONTAINER` is unset** (as in ECS) they connect to RDS over
**TCP with psycopg**, using `PGHOST/PGPORT/PGUSER/PGPASSWORD/PGDATABASE` — all injected by this
stack, with `PGCONTAINER` deliberately never set on the task. `psycopg[binary]` + `psycopg-pool`
are in `company/api/requirements.txt` and `libpq5` is in the image. No code change is needed to
deploy; verified end-to-end by a fresh-DB rehearsal (all migrations → build.py → post-build seeds
→ the live API served agents/goals/infra/permissions/users over TCP).

## Deploy

Prereqs: AWS credentials with admin-ish access, Terraform ≥ 1.5, Docker.

### Every deploy: `./deploy.sh`

Once the stack exists and secrets are set (first-time steps below), **every subsequent deploy is
one command** from the repo root:

```bash
./deploy.sh                 # build (amd64) → push → migrate → roll → health-check
./deploy.sh --skip-build    # image already pushed — just migrate + roll
./deploy.sh --skip-migrate  # code-only change, no new migrations
./deploy.sh --build-only    # build + push only
# env overrides: PROJECT=agency-agents ENV=staging REGION=us-east-1 ./deploy.sh
```

- Builds `linux/amd64` with `--provenance=false` — Fargate is amd64 and **cannot pull a Mac
  (Apple Silicon) arm64 image** or a manifest-list+attestation build.
- **A failed migration ABORTS before the service is rolled**, so a bad migration never goes live;
  the script dumps the migrate task's last log lines so you can see why.
- Every push is tagged `:latest` **and** `:<git-sha>` for rollback.
- Derives cluster / service / ECR repo / ALB from AWS at runtime (no hardcoded suffixes; no
  Terraform state needed) — override `PROJECT` / `ENV` / `REGION` via env.

This is the same pipeline as the CI workflow below, runnable by hand. The first-time / manual
walk-through follows.

### First-time setup (Terraform + secrets + first image)

```bash
cd infra
cp terraform.tfvars.example terraform.tfvars     # adjust region/image_tag if needed
terraform init
terraform apply                                  # creates VPC/RDS/ECR/ALB/ECS/S3/SSM

# 1) Set the real secret values (kept out of Terraform state):
PREFIX=/agency-agents-prod
aws ssm put-parameter --overwrite --type SecureString --name $PREFIX/OPENAI_API_KEY    --value 'sk-...'
aws ssm put-parameter --overwrite --type SecureString --name $PREFIX/AUTH_CEO_PASSWORD --value '...'
aws ssm put-parameter --overwrite --type SecureString --name $PREFIX/AUTH_CTO_PASSWORD --value '...'
aws ssm put-parameter --overwrite --type SecureString --name $PREFIX/AUTH_COO_PASSWORD --value '...'
aws ssm put-parameter --overwrite --type SecureString --name $PREFIX/AUTH_CIO_PASSWORD --value '...'
# (PGPASSWORD + AUTH_SECRET are generated by Terraform — no action needed.)

# 2) Build & push the app image to the ECR repo Terraform created:
REPO=$(terraform output -raw ecr_repository_url)
aws ecr get-login-password --region ap-southeast-1 | docker login --username AWS --password-stdin ${REPO%/*}
docker build -t "$REPO:latest" ..               # build context = repo root
docker push "$REPO:latest"

# 3) Seed the database so it matches the local baseline (RDS is private — run from a box
#    inside the VPC, temporarily set publicly_accessible=true, or use a bastion). ORDER MATTERS —
#    migrations are AGENT-INDEPENDENT; anything FK-referencing an agent is seeded AFTER build.py.
#    Point build.py at RDS over TCP by exporting the PG* vars (NO PGCONTAINER → TCP mode):
     export PGHOST=<rds-address> PGPORT=5432 PGDATABASE=<db_name> PGUSER=<db_username> PGPASSWORD=<pw>
#
#    a. Schema + FIXED reference data (owner accounts, permission catalog, model prices,
#       infra pricing, goals TABLE, ENG-OPS engagement, ch-general channel). Runs in filename order:
         for f in ../company/db/0*.sql; do psql "$DATABASE_URL" -f "$f"; done
#
#    b. AGENT ROSTER — derived from the repo's .md files by build.py, NOT stored in SQL. Runs
#       over TCP (psycopg). Easiest from inside the built image, which already has psycopg + repo:
         python ../company/ui/build.py            # or, from company/ui: npm run data
#
#    c. AGENT-DEPENDENT fixed data (goal rows + owners, Access-Tools-Admin grants/runtime):
         psql "$DATABASE_URL" -f ../company/db/seed/deploy_post_build.sql
#
#    d. STANDING command channels (Leadership / HR) + members:
         psql "$DATABASE_URL" -f ../company/db/seed/standing_channels.sql
#
#    Owner passwords are set at app startup from AUTH_*_PASSWORD env (step 1). The
#    company/db/seed/sample_*.sql files are DEMO content — do NOT run them on a deploy.

# 4) Roll the service onto the new image + schema:
aws ecs update-service --cluster $(terraform output -raw ecs_cluster) \
  --service $(terraform output -raw ecs_service) --force-new-deployment

terraform output app_url                         # open this
```

## CI/CD — auto-deploy on merge to `main`

`.github/workflows/deploy.yml` runs on every push to `main` (and manual dispatch):

1. **Build & push** the FE+BE image to ECR (tags `<sha>` + `latest`).
2. **Register** a new task-definition revision pointing at the new image.
3. **Migrate** — runs `company/db/migrate.py` as a one-off ECS task on that revision. Because
   the task runs *inside the VPC*, it reaches the private RDS; it applies migrations → `build.py`
   roster → post-build seeds over psycopg (no `psql` needed). The deploy **stops if this fails**.
4. **Roll** the ECS service onto the new revision and wait for `services-stable`.
5. **Health-check** `http://<alb>/api/health` (BE) and `/` (FE); the job fails if either isn't 200.

Infra itself (VPC/RDS/ALB) is intentionally **not** applied here — keep that a reviewed manual
`terraform apply`.

**One-time setup** (after the first manual `terraform apply` from the Deploy section):

```bash
# The stack creates the GitHub OIDC provider + a scoped deploy role. Wire it to GitHub:
gh secret set AWS_DEPLOY_ROLE_ARN --repo thinhsuy/doom-agents \
  --body "$(terraform output -raw github_deploy_role_arn)"
```

- The role trusts **only** `repo:thinhsuy/doom-agents` on `refs/heads/main` (change via the
  `github_repo` variable). If the account already has a GitHub OIDC provider, set
  `create_oidc_provider = false` in `terraform.tfvars` and the role reuses it.
- The SSM secrets (`AUTH_*_PASSWORD`, `OPENAI_API_KEY`, …) are set once (Deploy step 1); the
  pipeline never touches them. Owner passwords apply at app startup.
- The pipeline registers its own task-def revisions, so leave the service's `image_tag` alone;
  a `terraform apply` won't fight it (the app image is only read at task launch).

## HTTPS (optional)

Set `acm_certificate_arn` to an ACM cert in the same region → the ALB serves HTTPS on 443 and
redirects 80→443. Point your domain's DNS at `alb_dns_name`.

## Notes / honest caveats

- **`desired_count = 1`** on purpose: the WebSocket office hub broadcasts from in-memory state,
  so multiple tasks wouldn't share it. Scale out only after moving the hub to Redis/pub-sub.
- **`.session_secret` / `AUTH_SECRET`**: session tokens are signed with `AUTH_SECRET` (a stable
  value Terraform provisions in SSM and injects into the task env), so **logins survive redeploys
  and stay valid across tasks** — `_session_secret()` in `company/api/main.py` prefers it. Only
  when `AUTH_SECRET` is unset (local dev) does the app fall back to a per-process key persisted to
  `.session_secret` on disk. (After changing any SSM secret, the task must restart to re-read it,
  which `./deploy.sh` / a redeploy does.)
- **Terraform state holds the generated DB password** — store it in a secured backend (S3 +
  DynamoDB lock) for real use; it's local by default here and `.gitignore`d.
- **`skip_final_snapshot = true` / `deletion_protection = false`** for easy teardown — flip both
  for real prod so `terraform destroy` can't nuke the DB.
